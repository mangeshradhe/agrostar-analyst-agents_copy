Key findings

    Order outcome × reason — why calls need action

    Call-level counts, with the distinct orders behind each. In each cell the % is the share of that row (what drives that outcome); in the Total column it is the share of all calls in view. One order can have calls with different outcomes or reasons, so order counts don't add up across rows or columns.

    Call vs digital evidence — did the promised action actually happen?

    Order-level. Compares each order's last call outcome (confirmed / on hold / cancelled) against its package status history: did the matching digital action (delivered / put on hold / return initiated) actually get logged, and was it the same day (IST) as the call? "Not executed" means that day is over with nothing logged since — a real execution gap, not just a slow update. "Pending today" still has time left in the day.

    Agreed on the first call, but the order ended cancelled / returned

    Order-level. Population: orders whose first LMD call ended “delivery confirmed” (the farmer agreed to take delivery). “Turned” = the order later ended cancelled or returned — a package in a cancellation / return status, or the last call was a cancellation. The reason is read from the first later call that moved the order away from confirmed (on hold or cancelled); orders with no such call had the cancel / return logged without another call, so the cause isn’t on any call. Use the “Agreed first, then cancelled / returned” filter above to list these orders and open each journey.
